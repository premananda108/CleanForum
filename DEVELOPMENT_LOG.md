# Протокол Разработки "CleanForum"

Этот документ описывает ключевые этапы разработки, отладки и улучшения проекта "CleanForum".

## 1. Анализ и исправление сохранности данных (Персистентность Redis)

*   **Проблема:** При перезапуске контейнера Redis терялись все опубликованные посты.
*   **Анализ:** Файл `docker-compose.yml` использовал `volume` для хранения данных, но не гарантировал их сброс на диск перед остановкой.
*   **Решение:** В `docker-compose.yml` была добавлена команда `command: redis-server --appendonly yes`. Это включило режим AOF (Append Only File), который обеспечивает надежное сохранение каждой операции записи на диск.

## 2. Улучшение логики классификации спама

*   **Проблема:** Спам-сообщения, не похожие на обучающую выборку, публиковались как легитимные.
*   **Анализ:** Логика в `core/classification.py` была слишком "мягкой". Если система не находила похожих постов в базе, она полагалась на эвристику, которая требовала нескольких признаков спама для блокировки.
*   **Решение:** Логика была ужесточена. Теперь, если классификатор не находит в базе данных постов, похожих на новый, он из соображений предосторожности **всегда** блокирует его как подозрительный (`Post is too dissimilar from any known content`).

## 3. Исправление обновления статистики

*   **Проблема:** При обнаружении спама счетчики в `/api/stats` не обновлялись.
*   **Анализ:** В `main.py` код, увеличивающий счетчики, находился после блока проверки на спам. Если пост блокировался, выбрасывалось исключение, и код обновления статистики никогда не выполнялся.
*   **Решение:** Логика в эндпоинте `POST /api/posts` была изменена. Теперь счетчик `total_classified` увеличивается при каждой попытке публикации, а `spam_detected` — сразу после обнаружения спама, **до** выбрасывания исключения `HTTPException`.

## 4. Внедрение интеграционных тестов

Это был самый сложный этап, включавший несколько итераций.

*   **Цель:** Создать простые и надежные тесты для проверки ключевого функционала.
*   **Итерация 1: Сложные асинхронные тесты.** Первоначальная попытка использовать `pytest` с `anyio` и асинхронными фикстурами провалилась из-за множества глубоких и редких ошибок (`ImportError`, `SystemError: AST constructor recursion depth mismatch`, `RuntimeError: Event loop is closed`), связанных с конфликтами между версиями `pytest`, `anyio` и `Python`.
*   **Итерация 2: Отказ от асинхронности (неудачная).** Попытка полностью переписать приложение на синхронный код была предпринята, но прервана, так как это было избыточным решением.
*   **Итерация 3: Простые синхронные тесты (успех).**
    1.  **Подход:** Был выбран `fastapi.testclient.TestClient`, который позволяет писать тесты в синхронном стиле, "под капотом" управляя асинхронностью приложения.
    2.  **Решение проблем:**
        *   **Переменные окружения:** Проблема с подключением к тестовой базе данных Redis была решена путем установки `os.environ['REDIS_URL']` в самом начале тестового файла, до импорта приложения.
        *   **Изоляция тестов:** Проблема с созданием и очисткой индекса Redis была решена путем изменения области видимости (`scope`) фикстуры `client` на `function`, что гарантирует запуск каждого теста в абсолютно чистом окружении.
        *   **Тестирование фоновых задач:** Эндпоинт `/api/train` был доработан для поддержки синхронного выполнения в тестах (`background=false`), что позволило надежно проверять полный цикл работы системы.
*   **Результат:** Создан один файл `tests/test_integration.py`, содержащий простые и стабильные тесты, которые покрывают основной функционал приложения.
